# Tennis 冻结特征的 GT query 对应诊断

状态：2026-09-10已锁定，开发诊断协议。继承[因果三帧协议](tennis-temporal-probe-v1.md)的缓存、原始时间、标签和片段边界。仅使用game7开发窗口，最终测试比赛不进入。

## 为什么需要这一轮

简单三帧在seed0有净定位收益，仍存在背景亮点误选与困难位置失败。在增加对应模块之前，先判断“给定当前球位置，现有特征是否已经能够匹配到历史球”。如果GT query条件下仍大量检索到背景，扩大搜索范围本身不能被假定为修复。

这不是自动检测、正常点跟踪成绩或任何未来模型的性能上界。GT位置只构造诊断query并评价历史检索，后续真实模型仍须自己发现球；该诊断成功也不证明候选阶段能找到query。

## 数据与几何

使用 `data/cache/tennis/dinov3_convnext_tiny_512x288_step8_h2_s1`，stage1原生36×64格。每个格在原图中覆盖20×20像素，使用已有像素中心变换；query为当前GT所在原生格的192通道特征。历史帧间隔分别为1、2个真实帧。

只有当前与所检索历史帧都有合法位置标签的帧对进入本诊断，记录实际数量与visibility；不要求另一历史帧也有位置。该条件仅限制可评价的oracle帧对，不能反过来过滤正常训练/验证目标。球真实尺寸未知，不计算伪造的rho。

两端GT落在同一原生格与不同格的情况分开报告。同格成功可能由稳定背景产生，不能当作已经找到了运动球。原图中心位移和native格位移各有明确单位，不混为球大小。

## 两个描述子对照与搜索

第一组对原始每格向量作L2归一化并计算cosine。第二组先对每帧、每个通道减去空间均值，再作同样的L2归一化与cosine；这只是去掉公共分量的简单对照，不声称解耦相机运动、物体运动或实现新颖motion subspace。

搜索分别使用全图和以当前GT格为中心、Chebyshev半径2/4/8格的正方形窗口；窗口在图像边缘截断。局部范围按格定义，不能把格中心窗口与原始连续坐标的严格半径混用。所有候选仍来自历史帧，所有描述子条件共享帧对。

## 应保存什么证据

每个帧对记录game/clip、两端原始帧号、间隔、visibility、真实中心位移、检索位置和误差。对于每个局部/全局搜索，分别报告真实历史GT所在格的几何覆盖、实际预测位置的PCK@16/32及误差；PCK的分母包括几何未覆盖的帧对，不能只在成功覆盖子集上计算。

这里的覆盖特指GT所属格进入候选集，不是PCK@16的严格上界：相邻格中心也可能落在16px容差内。关于范围和匹配的解释需保留这个几何区别。

全局搜索另记录真实历史格的相似度排名、top-k检索情况，以及真历史格相似度减当前同坐标历史格相似度。排名是格检索指标，PCK是原图坐标指标，不能互相替代。按全体、双端easy、两端跨格和clip汇总；不同组样本数同时保留。乐观排名为“1+严格更高分个数”，实际argmax/top-k在并列时按较小格索引优先，不能让乐观并列名次冒充唯一top1正确。

## 验证与计算边界

以已知向量和已知空间位移的小例子，确认全局能找到真对应、较小窗口确实排除它，且当前位置与历史真位置不会互换。坐标转换复用既有测试覆盖的函数，不另写第二套坐标逻辑。

仅使用CPU和已经落盘的确定性特征，不解码图像、不再次运行backbone、不保存重复特征。时间计量是开发诊断成本，不能替代训练模型或在线视频推理成本。

结果将决定优先研究查询/描述子、搜索覆盖还是背景竞争；不从本轮直接选定新的模型架构，也不凭单一game声称普遍规律。
