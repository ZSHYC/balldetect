# Tennis 因果三帧开发协议

状态：已锁定的开发诊断协议；2026-09-10。继承 [空间探针协议](tennis-spatial-probe-v1.md) 的数据/标签版本、坐标、指标和 game1–6 train / game7 val；game8–10 不参与。

## 本轮要分清的问题

空间读出容量已被证实是重要因素，不能以最弱单帧头作 motion 对照。本轮采用已实现的 hidden32 非线性头，在同一开发目标集合上比较当前帧、三帧拼接、当前帧重复三次。它们只是机制基线，不是论文创新。

初次时序诊断用 512×288、ConvNeXt-Tiny stage1、output stride4。该输入成本低且已有可信读出起点；1024×576 空间对照提供增加空间采样的独立替代解释。后续主尺度根据结果决定，不通过查看测试比赛选择。

## 时间与样本

目标原帧号仍满足 `frame_id % 8 == 0`，上下文必须是同一个 game/clip 的真实 `t−2,t−1,t`。不足或缺失上下文时整个目标窗口排除，所有对照用完全相同的目标集合。不能拿上一条稀疏采样记录当 t−1，不重复片段第一帧补齐时间，也不跨 clip。

上下文视觉读取不依赖其有无位置标签；只有目标监督要求合法位置或明确无球。未知/非法的历史位置不能阻止使用真实历史图像。Tennis 当前开发发布包没有这个异常，但实现和测试保留语义。目标窗口不会要求双端可见，避免过滤掉最需要 motion 的困难样本。

输出为当前帧，无未来输入及前瞻等待；输入历史长度 2 帧。数据包只有 clip 内帧号，30 fps 来自论文，不伪造 PTS。

## 三个对照

- `current`：只读取当前帧特征，使用既有非线性单帧头，在新的共同目标集合重新训练。
- `stack`：按时间顺序拼接三个冻结特征，每帧独立无仿射 GroupNorm，随后同样的 hidden32 空间头与无球头。真实输入是三帧。
- `repeat`：只读取当前帧，将完整通道块重复三次，使用与 stack 完全相同的头/初始化规则。它控制重复参数化和优化的影响；不是“去掉真实世界运动”的因果反事实。

保留当前和历史的完整特征拼接与保留当前加若干有符号差分，在无额外非线性/约束时可以互相线性转换。因此不把这两种输入简单重参数化当作不同的新 motion 表征，也不机械增加差分实验数量。帧差是变化证据，仍不是位移真值。

初筛固定 seed0、AdamW(lr .003, weight_decay .01)、batch16、30epoch，按同一 val PCK@16 再 PCK@8 选优。头参数量随输入通道变化分别报告；repeat 与 stack 完全相同。输入缓存、原图输出网格、目标标签、评价和采样一致。以后主比较须增加重复运行和完整训练；初筛不支撑论文性能声明。

## 缓存与归因

每个真实帧最多保存一次，通过窗口索引组合，不落盘重复窗口。已有相同骨干/预处理的当前帧缓存可复制特征行复用，只对缺失历史帧解码和 forward。旧空间对照缓存保留以复现已完成实验；待尺度与方法收敛再按实际复用价值清理。

训练读取窗口索引时只用 `window[-1]` 的标签。缓存提供 context 不代表 current 对照可以使用历史通道。保存逐帧预测以分析净救回：单帧错→时序对和单帧对→时序错同时报告，全集与各 visibility 分开，不能只展示救回样例。

效率记录区分一次提取、缓存读出训练和未来连续推理。相邻推理共享历史 backbone 结果的潜力不等于已经实测在线吞吐。存在分类仍需独立报告；上一阶段的始终有球问题不因时序输入而被默认解决。
